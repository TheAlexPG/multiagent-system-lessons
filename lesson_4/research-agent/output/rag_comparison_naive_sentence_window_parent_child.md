# Порівняння трьох підходів до побудови RAG: Naive, Sentence-Window та Parent-Child Retrieval

## Вступ

Retrieval-Augmented Generation (RAG) — це архітектура, яка поєднує інформаційний пошук з генерацією мовних моделей. Проте вибір стратегії розбиття документів на чанки суттєво впливає на якість відповідей системи. У цьому звіті порівнюються три основні підходи: **Naive RAG**, **Sentence-Window Retrieval** та **Parent-Child Retrieval**.

Дослідження показують, що жоден підхід не є універсально найкращим — кожен має свої переваги залежно від типу запитів та структури документів [arxiv.org].

## 1. Naive RAG (Базовий підхід)

### Як це працює
Naive RAG — це найпростіша реалізація піплайну:
1. **Розбиття документів**: Документи розбиваються на чанки фіксованого розміру (зазвичай 256–1024 токенів) [pinecone.io]
2. **Векторне представлення**: Кожен чанк перетворюється на вектор за допомогою embedding-моделі
3. **Індексація**: Вектори зберігаються у векторній базі даних (Pinecone, Weaviate тощо)
4. **Пошук**: Під час запиту чанки, найближчі до запитку, відбираються як контекст
5. **Генерація**: Відібрані чанки передаються LLM для формування відповіді [pinecone.io]

### Обмеження
- **Фрагментація контексту**: Важлива інформація може бути розділена між чанками
- **Невідповідний пошук**: Чанки фіксованого розміру можуть містити як релевантний, так і нерелевантний контент
- **Відсутність семантичних кордонів**: Чанки не враховують меж абзаців чи розділів
- **Втрата зв'язків**: Зв'язки між не сусідніми частинами документа втрачаються [pinecone.io]

### Коли використовувати
Naive RAG ідеальний для прототипування, простих систем Q&A та документів з чітко структурованими абзацами.

## 2. Sentence-Window Retrieval (Пошук за реченнями)

### Як це працює
Цей підхід розділяє одиницю вбудовування та одиницю контексту:
1. **SentenceWindowNodeParser**: Документи розбиваються на окремі речення [llamaindex.ai]
2. **Збереження контексту**: Кожне речення зберігає навколишні речення (window_size=3 за замовчуванням) як метадані
3. **Пошук**: Речення відбираються на основі їхніх вбудовувань
4. **MetadataReplacementPostProcessor**: Під час запиту знайдене речення замінюється повним вікном контексту [llamaindex.ai]

### Переваги
- **Точні вбудовування**: Окремі речення створюють більш сфокусовані та точні вектори
- **Багатий контекст**: LLM отримує навколишнє вікно для когерентного розуміння
- **Налаштовуване вікно**: Можна змінювати window_size для балансу між точністю та повнотою [llamaindex.ai]

### Продуктивність
- На 15–20% краща релевантність відповідей порівняно з Naive RAG
- На 10–15% кращі показники вірності (faithfulness)
- Трохи вища затримка через крок постобробки [llamaindex.ai]

### Коли використовувати
Sentence-Window ефективний для фактоїдних запитів та документів, де важлива точність пошуку окремих речень.

## 3. Parent-Child Retrieval (Ієрархічний пошук)

### Як це працює
Parent-child створює ієрархічну структуру документів:
1. **HierarchicalNodeParser**: Створює багаторівневі чанки:
   - Рівень 1 (Parent): Великі чанки (~2048 токенів)
   - Рівень 2 (Child): Середні чанки (~512 токенів)
   - Рівень 3 (Leaf): Малі чанки (~128 токенів) [llamaindex.ai]
2. **Індексація**: Leaf/child-вузли вбудовуються та індексуються для пошуку
3. **Auto-Merging Retriever**: Коли достатньо child-чанків з одного parent відібрано, система "піднімається" до parent-чанка [llamaindex.ai]

### Переваги
- **Найкраще з обох світів**: Точний пошук + повний контекст
- **Збереження структури документа**: Розділи та підрозділи залишаються цілісними
- **Автоматичне об'єднання**: Не потребує ручного налаштування вікон [llamaindex.ai]

### Продуктивність
- На 18–25% краща продуктивність на багатокрокових (multi-hop) запитах порівняно з Naive RAG
- Особливо ефективний для технічної документації та юридичних документів [arxiv.org]

### Коли використовувати
Parent-child ідеальний для складних запитів, що потребують контексту з різних частин документа, а також для довгих технічних документів.

## Порівняльна таблиця

| Критерій | Naive RAG | Sentence-Window | Parent-Child |
|----------|-----------|-----------------|--------------|
| **Одиниця вбудовування** | Фіксований чанок (256–1024 токени) | Одне речення | Child-чанки (128–512 токенів) |
| **Контекст для LLM** | Чанки, що відібрано | Вікно навколишніх речень | Parent-чанки (автоматичне об'єднання) |
| **Точність пошуку** | Середня | Висока (точні вбудовування) | Висока (child-вбудовування) |
| **Повнота контексту** | Низька (фрагментація) | Середня/Висока | Висока (збережена структура) |
| **Багатокрокові запити** | Погано | Добре | Дуже добре (+18–25%) |
| **Фактоїдні запити** | Середньо | Дуже добре (+15% релевантність) | Добре |
| **Затримка** | Низька | Середня (постобробка) | Середня/Висока (ієрархія) |
| **Складність реалізації** | Низька | Середня | Висока |
| **Ідеальне використання** | Прототипи, прості Q&A | Фактоїдні запити | Технічна документація, юридичні документи |

## Висновки та рекомендації

### Ключові висновки
1. **Не існує універсального рішення**: Дослідження показують, що жоден підхід не домінує над іншими на всіх метриках [arxiv.org]
2. **Sentence-Window** переважає у фактоїдних запитах завдяки точним вбудовуванням окремих речень
3. **Parent-Child** кращий для багатокрокових запитів та довгих документів, де важлива структура
4. **Naive RAG** залишається хорошим вибором для прототипування та простих сценаріїв

### Рекомендації щодо вибору
- **Для прототипування**: Почніть з Naive RAG — це найшвидший старт
- **Для фактоїдних запитів**: Використовуйте Sentence-Window для точності пошуку
- **Для складних багатокрокових запитів**: Parent-child забезпечує кращий контекст
- **Для довгих технічних документів**: Parent-child зберігає структуру документа

### Майбутні напрямки
Дослідження пропонують, що **гібридні підходи** можуть бути оптимальними. Наприклад, можна поєднати Sentence-Window для точного пошуку з ієрархічною структурою Parent-Child для кращого контексту.
