# Порівняння підходів до побудови RAG: Naive vs Sentence-Window vs Parent-Child Retrieval

## 1. Вступ

Основною проблемою класичного RAG є втрата контексту при сегментації документів на маленькі чанки (chunks). Якщо чанок занадто малий, модель не отримує достатньо інформації для розуміння запитання. Якщо чанок занадто великий, це призводить до "шуму" та виходу за ліміт токенів моделі.

Існують три основні архітектурні підходи для вирішення цієї дилеми:
1.  **Naive RAG** (Базовий): Пошук у чанках, генерація на основі чанків.
2.  **Sentence-Window**: Збереження метаданих про сусідні речення для відновлення контексту після пошуку.
3.  **Parent-Child Retrieval**: Пошук у дрібних чанках, але завантаження великих "родительських" чанків для генерації відповіді.

Нижче наведено детальний аналіз кожного підходу, їхні переваги та недоліки.

---

## 2. Опис підходів

### 2.1. Naive RAG (Базовий підхід)
Це найпростіша архітектура, яка використовується за замовчуванням у більшості фреймворків (наприклад, LangChain).

*   **Механізм:**
    1.  Документ розбивається на чанки фіксованої довжини (наприклад, 500 токенів) з певним перекриттям (overlap).
    2.  Кожен чанок індексується окремо у векторній базі даних.
    3.  При запиті система знаходить найбільш релевантні чанки.
    4.  Знайдені чанки безпосередньо передаються LLM для генерації відповіді.

*   **Проблема:**
    *   Втрата контексту: Якщо важлива інформація розділена між двома сусідніми чанками, жоден з них не містить повної картини.
    *   Нестабільність відповідей: LLM може неправильно інтерпретувати абревіатури або займенники (наприклад, "вона", "це"), якщо контекст не є явним у межах одного чанка.

### 2.2. Sentence-Window Retrieval
Цей підхід запроваджено для збереження локального контексту без збільшення розміру векторного пошуку.

*   **Механізм:**
    1.  Документ розбивається на чанки, але **кожен чанок містить лише одне речення** (або дуже короткий текст).
    2.  Під час індексації до кожного вектора зберігаються метадані: посилання на попередні та наступні $N$ речень (наприклад, по 5 речень зліва і справа).
    3.  При запиті система знаходить релевантне "ключове" речення.
    4.  Система **не** шукає в базі великі чанки. Натомість вона використовує метадані, щоб відновити навколишні речення з оригінального документа (або з кешу) і сформувати повний контекст для LLM.

*   **Перевага:**
    *   Висока точність пошуку: оскільки чанки маленькі, векторний пошук знаходить саме ключові фрази.
    *   Збереження локального контексту без "шуму" великих блоків тексту.

### 2.3. Parent-Child Retrieval (Дочірньо-батьківський)
Цей підхід є найбільш потужним для складних документів, де важливо мати як точний пошук, так і широкий контекст.

*   **Механізм:**
    1.  **Розбиття (Splitting):** Документ розбивається на два рівні:
        *   **Child Chunks (Дочірні чанки):** Дуже маленькі (наприклад, одне речення або абзац). Вони індексуються у векторній базі для пошуку.
        *   **Parent Chunks (Батьківські чанки):** Більші блоки тексту, які містять дочірні чанки (наприклад, 1000+ токенів). Вони **не** індексуються у векторній базі для пошуку, а зберігаються як окремі об'єкти або в окремій колекції.
    2.  **Пошук:** Система шукає релевантні *Child Chunks*.
    3.  **Відновлення:** Після знаходження дочірнього чанка, система автоматично знаходить його "батьківський" чанок (за ID або посиланням).
    4.  **Генерація:** LLM отримує на вхід *Parent Chunk*, який містить повний контекст навколо ключової фрази.

*   **Перевага:**
    *   Ідеальна точність пошуку (через маленькі чанки).
    *   Повний семантичний контекст для LLM (через батьківський чанок).
    *   Уникає проблеми "обрізаного" тексту, яка часто трапляється при Naive RAG.

## 3. Порівняльна таблиця

| Характеристика | Naive RAG | Sentence-Window | Parent-Child Retrieval |
| :--- | :--- | :--- | :--- |
| **Розмір чанка для пошуку** | Великий (500–1000 токенів) | Дуже малий (1 речення) | Дуже малий (1-2 абзаци) |
| **Що передається LLM?** | Знайдений чанок | Відновлений контекст з метаданих | Батьківський чанок (Parent Chunk) |
| **Точність пошуку** | Середня/Низька (шум, втрата деталей) | Висока (точне попадання у фразу) | Дуже висока (точний пошук + контекст) |
| **Контекст для LLM** | Обмежений розміром чанка | Локальний (сусідні речення) | Широкий (цілий блок/абзац) |
| **Складність реалізації** | Низька | Середня (потрібна логіка відновлення) | Висока (потрібне управління ієрархією ID) |
| **Витрати на зберігання** | Низькі | Середні (залежить від кількості метаданих) | Вищі (дублювання тексту в Parent/Child) |
| **Затримка (Latency)** | Низька | Середня (потрібно зчитати сусідні речення) | Середня/Висока (два етапи: пошук + відновлення) |
| **Найкраще застосування** | Прості FAQ, короткі документи | Технічна документація, код | Юридичні документи, наукові статті, складні звіти |

## 4. Глибинний аналіз та порівняння

### 4.1. Точність пошуку (Retrieval Accuracy)
*   **Naive:** Часто страждає від "негативного впливу" великих чанків. Якщо у чанку є 500 токенів, але релевантним є лише 50 з них, векторний пошук може пропустити цей чанок через розмитість семантики.
*   **Sentence-Window & Parent-Child:** Обидва підходи використовують дрібні чанки для індексації. Це дозволяє векторній базі точно "влучити" в конкретну фразу, що відповідає запитанню користувача.

### 4.2. Якість контексту (Context Quality)
*   **Naive:** LLM отримує текст, який може бути обірваним посередині речення або абзацу. Це погіршує розуміння займенників та логічних зв'язків.
*   **Sentence-Window:** Контекст обмежений кількістю сусідніх речень (наприклад, 10). Це добре для фактологічних запитань ("Хто був президентом у 2020?"), але може не вистачити для складних логічних висновків.
*   **Parent-Child:** LLM отримує "батьківський" чанок, який зазвичай містить цілий абзац або розділ. Це забезпечує максимальну глибину контексту без втрати точності пошуку.

### 4.3. Витрати та складність
*   **Naive:** Найпростіший у впровадженні. Не потребує додаткових інструментів.
*   **Sentence-Window:** Вимагає спеціалізованих інструментів (наприклад, `SentenceWindowRetriever` в LangChain), які автоматично зберігають посилання на сусідні чанки під час індексації та відновлюють їх при запиті.
*   **Parent-Child:** Найскладніший у реалізації. Вимагає створення двох рівнів ієрархії (Parent/Child), правильного прив'язування ID та часто використання спеціальних інструментів (`ParentDocumentRetriever`). Також вимагає більше місця для зберігання, оскільки текст дублюється.

## 5. Висновки

Вибір підходу залежить від типу ваших документів та складності запитань:

1.  **Обирайте Naive RAG**, якщо:
    *   У вас прості документи (FAQ, короткі описи).
    *   Вам потрібна максимальна швидкість та мінімальні витрати на розробку.
    *   Контекст не є критичним для правильної відповіді.

2.  **Обирайте Sentence-Window**, якщо:
    *   Ви працюєте з кодом, технічною документацією або фактологічними даними.
    *   Вам важливо точно знайти конкретну фразу, але контекст не повинен бути надмірно великим.
    *   Ви хочете уникнути складності Parent-Child, але отримати кращий результат, ніж Naive.

3.  **Обирайте Parent-Child Retrieval**, якщо:
    *   У вас складні довгі документи (юридичні контракти, наукові статті, фінансові звіти).
    *   Запитання вимагають глибокого розуміння контексту та логічних зв'язків.
    *   Точність відповіді є пріоритетом над витратами на обчислення та зберігання.

**Рекомендація:** Для більшості сучасних промислових застосувань, де важлива якість відповідей, **Parent-Child Retrieval** вважається "золотим стандартом", оскільки він поєднує точність дрібного пошуку з багатим контекстом для LLM.
